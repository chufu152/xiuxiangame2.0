## 共享几何契约（`shared/geo/hex.gd`，**本里程碑的关键阻塞项**）

纯函数、无状态、不依赖节点；服务端与客户端**必须共用**同一套换算，避免两端口径漂移。**必须实现以下 7 个静态函数**（签名与调用方一致，不得改名）：

```gdscript
static func id(q: int, r: int) -> String                       # -> "q{q}_r{r}"
static func coords(tile_id: String) -> Vector2i                # -> Vector2i(q, r)
static func neighbors(cell: Vector2i) -> Array[Vector2i]       # 六邻接（用 DIRECTIONS）
static func distance(a: Vector2i, b: Vector2i) -> int          # 轴向距离
static func to_world(q: int, r: int, size: float = 1.0, height: float = 0.0) -> Vector3
static func opposite(edge: int) -> int                         # 边 i 的反向边（i+3 mod 6）
static func edge_vertices(q: int, r: int, edge: int, size: float = 1.0, height: float = 0.0) -> Array[Vector3]
```

- 世界坐标（flat-top）：`x = size * 1.5 * q`，`z = size * sqrt(3) * (r + q / 2.0)`，`y = height`。
- 边索引与 `DIRECTIONS`（`E(1,0)/NE(1,-1)/NW(0,-1)/W/SW/SE`）一一对应；`edge_vertices` 返回该边的两个端点（河流贴边渲染用）。
- `height` 由 `map.relief` 柱高系数（FLAT 1.0 / HILL 1.7 / MOUNTAIN 3.0）给出；客户端渲染与单位落点都用它。

## 服务端任务（`server/scripts/`，只在权威层）

- `rng/RngService.gd`：集中随机源（`RandomNumberGenerator`，种子来自 `newGame`；记录调用序号）；**所有**随机只经此，禁止各处私自 `new`。
- `model/`：枚举（境界/站位/灵根/派系/节点类型/基底/海拔/地貌/建筑/区域/改良/兵种/指令/资源）、`HexTile`（含 §6.5 全部新字段：`baseTerrain,relief,features[],riverEdges[],danger,ownerSectId,nodeId,districtId,workedByPeakId,improvementId,luxuryType`）、`GameNode`、`Sect`、`Disciple`、`SpiritPeak`、`GameState`。
- `rules/MapGenerator.gd`，分层生成（§4.1）：
  1. 基底（灵田/灵壤/荒土）；
  2. 海拔：用**连续山脊噪声**生成丘陵/山岳（不要单点孤立），保证出现**连绵多格山脉**；**先保护出生点邻域再排名选山**，避免为满足比例而破坏出生可通行性；
  3. 地貌（灵林/雾泽，山岳顶不叠）；
  4. 河流：从山岳/丘陵起源、向低海拔连续流到地图边缘，**河流是地块边**（成对边标记、端点连续），每个起源 1–2 个连续边；
  5. 险地、节点（按地形偏好）、奢侈资源；
  6. 出生点：中心玩家 + 3 个方向 AI；出生点附近保证安全（无险地、无山岳封死、可走通、有近水/灵田资源，按 §4.1.10/§4.3）。
- `rules/SetupInitializer.gd`：4 宗（1 玩家 + 3 AI）；每宗 1 主峰（人口 3/容量 10/防御 10）、1 名金丹宗主 + 2 名炼气外门弟子；初始资源灵气 400/灵石 300/工力 120/声望 0 + 天晶 2/玄铁 2/灵木 4。
- `rules/VisionCalculator.gd`：按视野半径（灵峰 3、节点 2；弟子 炼气 2/筑基 2/金丹 3/元婴 3/化神 4；站丘陵 +1）算每宗 `visibleTiles`/`exploredTiles`（R1 开局初始视野；随回合重算在 R2）。
- 命令：`newGame`、`getState`；`StateView` 构造 §6.5 视图（含 tiles 新字段、nodes、sects、disciples、spiritPeaks、visible/explored、当前玩家视角的迷雾）。
- **`newGame params` 字段名以 PRD §6.7 为准**：`{playerFaction, sectName, mapWidth, mapHeight, randomSeed, difficultyId}`；为兼容早期写法，额外接受别名 `factionType`→`playerFaction`、`difficulty`→`difficultyId`（同义重复且取值不一致时报 `BAD_PARAMS`）。缺省宽高取 `map.defaultWidth/Height`，`randomSeed` 可空（空则由集中随机源生成），`difficultyId` 缺省 `normal`。

### 协议级潜在缺陷（R1 暴露并修复，影响后续所有里程碑）

- **WebSocketPeer 默认收发缓冲仅 64 KiB**，而 `newGame` 的 view 快照随地图线性增长（默认 20×15=300 格约 70 KB，128×128 约 4 MB），导致**默认地图**上 `newGame`/`getState` 响应帧静默发送失败（`wsl_peer.cpp:784 _send` 报 `ERR_OUT_OF_MEMORY`）。R0 只发 hello/ping 小帧，故未暴露。
- 修复：`shared/protocol/msg.gd` 新增 `FRAME_BUFFER_BYTES = 16 MiB`，服务端 `NetServer`（`accept_stream` 之前）与客户端 `NetClient`（`connect_to_url` 之前）统一设置 `inbound/outbound_buffer_size`。**缓冲上限必须在建连前设置**，否则无效。
