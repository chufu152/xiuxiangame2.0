## 任务 0：先修 R1 端到端冷启动竞态（硬门禁，必须先全绿）

**现象**：当前 `tools/check.ps1` 在 [8/10] 客户端端到端段 5 项失败。实测用与 Launcher 相同的命令冷启动 headless 服务端，到端口可连接的耗时为 **2.18s / 6.49s / 19s**（波动极大）。

**根因（三处，都要修）**：

1. **拉起服务端后的就绪等待窗口太短**（`client/scripts/net/Session.gd` + `NetClient.gd`）：首连失败后 `Session._on_connect_failed()` 调 `Launcher.launch()`，固定 `await 0.5s` 后只重连一轮；`NetClient` 单轮 5 次尝试在「端口无监听→立即拒绝」下仅约 4.5s 退避窗口，随后 `_on_connect_failed` 因 `server_pid>0` 直接 `return`，**永久放弃**。服务端冷启动超过约 5s（6.49s、19s）即永远收不到 hello。
2. **自检断言误判**（`tools/check.ps1` 479–487 行）：`-match '<中文 label>'` 对 `R1_CLIENT_PASS:` 与 `R1_CLIENT_FAIL:` 两类输出都匹配，导致 FAIL 也被判 PASS。
3. **测试失败时残留子进程**（`client/tests/R1ClientTest.gd` 的 `integration()`）：`supports("newGame")` 不满足时 124 行提前 `return`，没走到 148 行 `session.shutdown()`，拉起的服务端不被回收。

**改法（写死，不允许另起设计）**：

1. 增加「拉起后等待就绪」逻辑：`Launcher.launch()` 成功后，进入轮询等待，**每 0.5s 尝试连接一次，直到 `supports("newGame")` 为真或总超时 `SERVER_READY_TIMEOUT_SEC = 40s`**（必须大于实测 19s 冷启动并留余量）；在已拉起（`server_pid>0`）期间连接失败**不得终止、不得重复 launch**。建议在 `Session` 用 async 循环实现，`NetClient` 保持纯传输职责；可复用 `run_dev.ps1` 已有的「TCP 端口轮询就绪」思路（不要靠固定 sleep 或日志匹配）。
2. `client/tests/R1ClientTest.gd`：`integration()` 等待 hello 的 deadline 由 **25000ms 提高到 45000ms**；任何提前返回路径（含 hello 超时、断言失败）都必须先 `session.shutdown()`。
3. `tools/check.ps1` 479–487 行端到端断言统一改为匹配 **`R1_CLIENT_PASS: <label>`** 前缀（如 `R1_CLIENT_PASS: 实际 Launcher/NetClient 收到 newGame hello`），使 FAIL 不再误判。

**验收（任务 0）**：

- 连续 **5 次冷启动** `--integration`（每次先确保无残留 godot）均 `R1_CLIENT_RESULT=OK`，5 次全绿；
- 人为制造慢启动（高负载或临时延迟就绪）时不卡死、40s 内可连上；失败路径无残留 godot；
- `tools/check.ps1` 全段恢复全绿（R0/R1 断言不回归）。

## 任务 2：移动规则（服务端 `server/scripts/rules/MoveRules.gd`，新建）

全部静态、无状态、只读 `config`，数值只取自 `data/gameConfig.json`。

1. `calculate_max_move_points(disciple: Disciple, config: Dictionary) -> int`：
   ```
   config["disciple"]["baseMovePoints"]
     + config["map"]["setup"]["realmMoveBonus"][disciple.realm]
     + Σ config["map"]["setup"]["rootMoveBonus"][root]   # 遍历 disciple.spiritRoots 的每一个（裁决一）
     + config["warfare"]["unitClasses"][disciple.unitClass]["moveBonus"]   # R2 只有 PU_TONG=0
   ```
   **R2 不做**道法 MOVE_BONUS（R4）、道路 startTileBonus（R3）。
2. `is_passable(tile: HexTile, config: Dictionary) -> bool`：取 `config["map"]["relief"][tile.relief]["passable"]`（MOUNTAIN 为 false）。
3. `crosses_river(from: HexTile, to: HexTile) -> bool`：求 `from → to` 的方向索引 `d`（在 `Hex.DIRECTIONS` 中定位 `to == from + DIRECTIONS[d]`）；当 `from.riverEdges.has(d)` 或 `to.riverEdges.has(Hex.opposite(d))` 为真即跨河（河流边在 `MapGenerator` 成对写回，见 186–191 行）。
4. `step_cost(config: Dictionary, from: HexTile, to: HexTile) -> int`（**进入 `to` 的代价**）：
   - 不可通行（MOUNTAIN）返回一个调用方用来排除的标记（建议返回 `-1`，由 BFS 先过 `is_passable` 跳过，不进入累加）；
   - 否则：
     ```
     cost = config["map"]["relief"][to.relief]["moveCost"]
     for f in to.features: cost += config["map"]["features"][f]["moveExtra"]
     if to.danger: cost += config["map"]["dangerTileMoveCost"]     # =1（裁决二）
     if crosses_river(from, to): cost += config["map"]["river"]["moveExtra"]  # =1
     return max(1, cost)
     ```
   - **R2 不做**敌方 ZOC（R5）、道路减耗（R3）。

## 任务 3：BFS 可达范围（服务端 `server/scripts/rules/MoveRangeCalculator.gd`，新建）

- 口径与 1.0 `MoveRangeCalculator.reachableCosts` 一致，`reachable(state, config, disciple) -> Dictionary`，返回 `{origin: String, costs: Dictionary, order: Array}`（GDScript Dictionary 保插入顺序；`order` 为 BFS 发现顺序，`costs` 为 tileId→最小代价）。
- 起点 `disciple.tileId`：`costs[origin]=0`、`order[0]=origin`。
- 队列展开：对当前格按 **`Hex.DIRECTIONS` 固定顺序**遍历六邻（`Hex.neighbors`），确定性唯一来源：
  - 邻格不存在 → 跳过；
  - `not MoveRules.is_passable(neighbor)` → 跳过（MOUNTAIN 不进高亮）；
  - `total = costs[current] + MoveRules.step_cost(config, current, neighbor)`；
  - `total > disciple.movePoints`（**当前剩余移动力**，不是 max）→ 跳过；
  - 邻格未记录或 `total` 更小（Dijkstra 松弛）→ 更新 `costs[neighbor]=total`、加入 `order` 并入队继续展开。
- **R2 不做**外交过境关（外交已裁剪）、ZOC、道路、单位占格阻挡、战斗触发；**可达性只由地形决定**（己方多个弟子开局同格，移动后仍可与队友同格）。

## 任务 4：移动命令（服务端，`server/scripts/rules/MoveAction.gd` 新建 + 在 `CommandDispatcher` 注册）

     `{discipleId, originTileId, movePoints, maxMovePoints, tileIds, costs, tileCount}`
